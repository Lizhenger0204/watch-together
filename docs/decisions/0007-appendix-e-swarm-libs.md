# ADR 0007 附錄 E：種子式散布的套件評估與原型（T-140）

> **草稿（T-140）**。規則見[附錄 D](0007-appendix-d-swarm.md)。查證日期 2026-11-27；版本與日期取自 npm registry。

## §1 要回答的問題

使用者擔心自己寫的東西日後難維護、遇到 bug 修不了。所以逐項檢查：能不能直接用現成套件做「收看者互相補片」，或至少把收看端最容易出錯的部分（MSE 緩衝與容量）交給成熟套件。

**結論**：

- (a) **不採用**：要整檔雜湊、片段與時間無關、mkv 不能播、收看端會拿到整部片，第二層無法用。
- (b) **不採用**：它的 peer 探索綁死公開 tracker，直接違反 IP 規則；它也假設有 HTTP 來源。能重用的只剩排程，但排程正是我們要依房主預算控制的部分。
- (c) **建議採用 hls.js（light build）**：把收看端 MSE 的建立、附加、容量不足時清除（`backBufferLength`）、卡住時微調（nudge）、跳轉到未緩衝的位置、iOS 的 ManagedMediaSource 交給維護活躍的專案；我們保留片段表、散布排程、對時與追趕（這些沒有現成套件）。shaka 也可行（`NetworkingEngine.registerScheme`），但體積是 2.5 倍、原型沒驗證，列為備案。
- (d) 是 (c) 驗證失敗時的退路（附錄 B、C 已寫好規則）。

**散布排程與信令沒有可用的套件**：三個套件的排程都假設「每人各自播放、彼此不同步、有 HTTP 或 tracker」。我們的情況是「全房同步、房主是唯一來源、房主決定配對」，所以排程自己寫（附錄 D §3～§4），但它是純函式、輸入輸出明確，可以完整單元測試。

**拆檔與封裝**：維持 mediabunny（附錄 A §5）。T-141 另評估用 mediabunny 的 fragmented MP4 輸出（`Mp4OutputFormat`，搭配不重新編碼的 encoded packet source）取代我們自己的 fMP4 封裝器，可以再少一塊自己維護的程式；要先確認它的 DTS 推導能通過附錄 B §3 的九種素材。

## §3 原型（`docs/decisions/assets/0007/swarm*.js`、`run-swarm.mjs`）

**做法**：房主拆檔（mediabunny 1.65.2）→ 每個 GOP 一段、影音同段的 fMP4 → 算 SHA-256 → 用 `pt-ctl` 公布並指派來源（附錄 D 的「房主協調」簡化版：每段直送 1 份，輪流給不同的人；急件直送給每個人）。收看端用 **hls.js 1.7.4 light** 播放，自訂 loader 從記憶體倉庫拿播放清單、init 與片段；倉庫的資料來自房主或其他收看者的 DataChannel，驗證通過才收。收看者之間全連（3 人時每人 2 個 peer）。與附錄 A 相同限制：**同一台 M1、同一個 Chrome、loopback**；同機時鐘相同，原型省略對時；追趕用簡化規則（落後或超前 > 0.4 秒且落點片段已在倉庫就跳、其他 ±5% 調速）；小塊雜湊與邊收邊轉沒做（整段收完才驗、才轉）。

**片源**：1080P H.264 15.2 Mbps（GOP 2 秒，150 秒）、720P H.264 5.1 Mbps（GOP 2 秒）。房主預算 77 Mbps，收看者上傳上限 40 Mbps。流程：每 2 秒加入一位 → 等 12 秒 → 量 20 秒穩態 → 房主往後跳 20 秒 → 量 12 秒（部分加測「最後一位離開、新的一位加入」）。原始 JSON：`results/swarm-*.json`。

| 情境 | 房主上傳（穩態） | 每位收看者：從房主／從其他人／上傳（Mbps） | 與房主誤差 p50／p95 | 加入→開播 | 跳轉後誤差 < 100 ms |
| --- | --- | --- | --- | --- | --- |
| 1080P，3 人，**不轉送**（對照） | 67（3 份 46，另有兩位仍在補超前量） | 15～26／0／0 | 25／41～49 ms | 1.1～5.1 秒 | 0.9～1.3 秒 |
| 1080P，3 人，**種子式** | **13.7**（約 0.9 份） | 4.5～4.6／9～11／9～12 | 7～25／9～41 ms | 1.2～2.6 秒 | 0.2～2.5 秒 |
| 1080P，3 人，C 不上傳 | 15.3 | A、B：7.6／9.1／18.3；C：0／18.3／0 | 7～25／9～41 ms | 1.2～2.6 秒 | 0.7～1.2 秒 |
| 1080P，3 人，B 竄改轉送的資料 | 13.7 | B 被排除後：A、C 由房主與彼此補 | 25／35～41 ms | 1.2～5.1 秒 | 0.7～3.2 秒 |
| 720P 5.1 Mbps，**5 人**，種子式 | **5.1**（1 份；全部直送要 25.7） | 1.0／4.1／4.1 | 24～25／41～42 ms | 0.3～1.2 秒 | 0.6～2.8 秒 |

- **竄改測試**：B 轉送時把每段中間一個位元組反轉。C 驗到 3 次不符，丟掉並改向房主要；房主收到 `bad` 後停止指派 B（原型一次檢舉就停用，正式規則要兩位以上，附錄 D §5）。**沒有任何被竄改的資料進入播放器**，全程未卡住。
- **離開與加入**：3 人穩態後 C 關閉分頁、D 加入：D 2.7 秒開播，加入後 12 秒內從其他人收 30.5 Mbps、從房主 22.8 Mbps。
- **跳轉**：所有人同時要新位置，房主前 3 秒直送給每個人（1080P 3 人：12 秒平均 74～79 Mbps，碰到預算上限）。附錄 D §4 的「小塊輪流送、邊收邊轉」是為了解決這個尖峰，原型沒做。
- **SHA-256**：4 MiB 約 2.3～2.5 ms（M1、`crypto.subtle.digest`）。
- **沒做成的**：
  - 1080P 15 Mbps **5 人**（較早版本的原型）：同一台 M1 上 6 個分頁各自解碼 1080P，加上 loopback 總流量，有 2 位收看者的 DataChannel 不再排空、播放停住，與附錄 A §2 的 loopback 停滯相同現象（`results/swarm-1080p15-n5-overload.json`）。
  - 4K 40 Mbps MKV（GOP 5 秒、每段 25 MB）**2 人**：收看者一直沒開播（`results/swarm-4k40-n2-stalled.json`）。原因是原型的兩個簡化：急件直送給每個人，加上整段 25 MB 收完才轉送——房主預算 50 Mbps 時，每段給兩人要 8 秒，比片段長度（5 秒）還久，永遠追不上。這正是附錄 D 要求「片段 ≤ 2 秒／4 MiB」與「急件也用小塊輪流送、邊收邊轉」的原因；1 人時正常。
  - 以上要在多台機器上用正式規則驗證（T-147）。

**hls.js 的實際問題**（寫進 T-142 的注意事項）：

1. 自訂 loader 的回呼必須是**非同步**，而且 `abort()` 要呼叫 `onAbort`；否則 hls.js 在第一次 `BUFFER_RESET` 後永遠停在 `FRAG_LOADING`（原型踩到）。
2. 影音同段的 fMP4，hls.js 建一個 `audiovideo` SourceBuffer；light build 沒有獨立音軌播放清單（alternate audio），所以影音要同段。
3. hls.js 以第一段的 `tfdt` 對齊播放清單時間（`initPTS`，原型的片從 0 開始所以一致）。附錄 B §3 的輸出時間軸要等於播放清單時間：起點不是 0、有 edit list、有起始空白的片，T-141 要用附錄 B §3 的素材驗證。
4. 長 GOP 切成的續接段不是獨立可解的。跳轉落在續接段時 hls.js 的行為未驗證；我們的追趕本來只跳到入口附近（附錄 C §3），T-142 要驗收「長 GOP 片跳轉」。
5. 播放清單要事先知道所有片段：MP4 從 `stss` 直接得到；MKV 靠 Cues。沒有 Cues 的 MKV 要掃描，大檔可能很慢，T-141 量測，太慢就這種片走第三層。
