# ADR 0007 附錄 E：種子式散布的套件評估與原型（T-140）

> **草稿（T-140）**。規則見[附錄 D](0007-appendix-d-swarm.md)、[附錄 F](0007-appendix-f-swarm-protocol.md)。查證日期 2026-11-27；版本與日期取自 npm registry。

## §1 要回答的問題

使用者擔心自己寫的東西日後難維護、遇到 bug 修不了。所以逐項檢查：能不能直接用現成套件做「收看者互相補片」，或至少把收看端最容易出錯的部分（MSE 緩衝與容量）交給成熟套件。

**結論**：

- (a)、(b) **不採用**。共同原因：兩者都缺少本專案必要的**成員授權、由房主決定的配對、依房主預算的排程**；這三件正是我們要自己控制的部分，用了套件也要繞過它的預設。另外 (a) 要先對整檔算 piece 雜湊、piece 與時間無關、第二層的轉碼輸出做不成 torrent；(b) 假設有 HTTP 來源（我們的來源是房主的 DataChannel，要把片段橋接到套件的 Fetch 介面，例如以 `httpRequestSetup` 傳回自訂 `Request`）。
- (c) **hls.js（完整版，要用獨立音軌）列為候選**：把收看端 MSE 的建立、附加、`backBufferLength` 清除、卡住時微調（nudge）、跳轉到未緩衝位置、iOS 的 ManagedMediaSource 交給維護活躍的專案。**T-141 的採用門檻**，全部通過才採用：
  1. 附錄 B §3 的時間軸：九種素材的首格時間、影音對齊與 `buffered` 連續性（含起點不是 0、edit list、起始空白）。
  2. **附錄 F §3 的分軌契約**：影像與音訊各自的 SourceBuffer、各自的 append window（AAC priming、音訊比影像短）。原型用影音同段、單一 `audiovideo` SourceBuffer，**不符合**也**沒有驗證**這一項；light build 沒有獨立音軌播放清單，所以若採用 hls.js，要用完整版（`hls.min.js` 壓縮後約 190 KB）的獨立音軌。不接受單一 SourceBuffer：要接受就得先修改附錄 F §3，並用同一批素材驗證。
  3. **附錄 F §2 的恢復流程**：`QuotaExceededError` 後開新 epoch 重新定位、ManagedMediaSource `endstreaming`／`startstreaming`（E 不在緩衝內時開新 epoch）、換 `pt-data` 時取消並重發請求，都能經由 hls.js 的設定或事件做到。
  4. hls.js 自己的 nudge 與跳轉不會干擾附錄 C §2 的追趕狀態機（量測同步誤差與額外跳轉次數）。
  5. 附錄 E §3 列的 hls.js 問題（自訂 loader、長 GOP 續接段跳轉、沒有 Cues 的 MKV）。
  shaka 也可行（`NetworkingEngine.registerScheme`），體積是 2.5 倍、原型沒驗證，列為備案。
- (d) 是 (c) 沒通過門檻時的做法（附錄 B、C 已寫好規則）。

**散布排程與信令自己寫**：現成套件的排程都假設「每人各自播放、彼此不同步、有 HTTP 來源或 tracker」。我們的情況是「全房同步、房主是唯一來源、房主決定配對」，所以排程自己寫（附錄 D §3～§4），但它是純函式、輸入輸出明確，可以完整單元測試。

**拆檔與封裝**：維持 mediabunny（附錄 A §5）。T-141 另評估用 mediabunny 的 fragmented MP4 輸出（`Mp4OutputFormat`，搭配不重新編碼的 encoded packet source）取代我們自己的 fMP4 封裝器，可以再少一塊自己維護的程式；要先確認它的 DTS 推導能通過附錄 B §3 的九種素材。

## §3 原型（`docs/decisions/assets/0007/swarm*.js`、`run-swarm.mjs`）

**做法**：房主拆檔（mediabunny 1.65.2）→ 每個 GOP 一段、影音同段的 fMP4 → 算 SHA-256 → 用 `pt-ctl` 公布並指派來源（附錄 D 的「房主協調」簡化版：每段直送 1 份，輪流給不同的人；急件直送給每個人）。收看端用 **hls.js 1.7.4 light** 播放，自訂 loader 從記憶體倉庫拿播放清單、init 與片段；倉庫的資料來自房主或其他收看者的 DataChannel，驗證通過才收。收看者之間全連（3 人時每人 2 個 peer）。與附錄 A 相同限制：**同一台 M1、同一個 Chrome、loopback**；同機時鐘相同，原型省略對時；追趕用簡化規則（落後或超前 > 0.4 秒且落點片段已在倉庫就跳、其他 ±5% 調速）；小塊雜湊與邊收邊轉沒做（整段收完才驗、才轉）。

**片源**：1080P H.264 15.2 Mbps（GOP 2 秒，150 秒）、720P H.264 5.1 Mbps（GOP 2 秒）。房主預算 77 Mbps，收看者上傳上限 40 Mbps。流程：每 2 秒加入一位 → 等 12 秒 → 量 20 秒穩態 → 房主往後跳 20 秒 → 量 12 秒（另一組加測「最後一位離開、新的一位加入」）。原始 JSON：`results/swarm-*.json`。

**量測定義與限制**：

- 「房主上傳」與每位收看者的上傳 Mbps：20 秒內**完整送出**的片段（最後一則交給 `send()` 之後才計入）的應用層位元組，不含 SCTP／DTLS 開銷，所以秒級數字會跳動；「從房主／從其他人」是收看端收齊的片段位元組。
- 「誤差」：收看端每 100 ms 採樣一次「畫面時間 − 應在時間」，**只在播放中、差距 ≤ 0.4 秒時採樣**；卡住、跳轉中的時段不在 p95 內。
- 「房主跳轉 → 回到 100 ms 內」：以房主的跳轉編號（`seekId`）辨識同一次跳轉，起點固定為第一則帶新編號的 `state` 的房主時刻；終點是跳轉之後、位於新位置的**第一張已呈現畫面**（`requestVideoFrameCallback` 回報）且以該畫面的顯示時刻算出的誤差 < 100 ms。**包含等資料的時間**。本次樣本都是**往後跳 20 秒**，「位於新位置」以 `mediaTime ≥ 目標 − 0.5 秒` 判斷；往回或小幅跳轉時這個條件分不出舊畫面，要改成綁定「該次跳轉完成後的新畫面」。
- 原型每段直送 1 份（`k = 1`），附錄 D §8 在 1080P 3 人時會用 `k = 3`（不需要散布）；這裡刻意用 `k = 1` 測散布本身。
- **單一台 M1、單次樣本、loopback**；收看者之間**全連**（3 人時每人 2 個 peer）；用 `BroadcastChannel` 代替有驗證的信令；同機時鐘相同、省略對時。

- **竄改測試**：B 轉送時把每段中間一個位元組反轉。C 驗到 4 次不符，丟掉並改向房主要；房主收到 `bad` 後停止指派 B（原型一次檢舉就停用，正式規則見附錄 D §5）。**沒有任何被竄改的資料進入播放器**；穩態沒有卡住，跳轉期間 A／B／C 各有 1 次 `waiting`，與其他組相近。
- **離開與加入**：3 人穩態後 C 關閉分頁、D 加入：D 1.7 秒開播，加入後 12 秒內從其他人收 30.5 Mbps、從房主 15.1 Mbps。
- **跳轉**：所有人同時要新位置，原型由房主把前 3 秒直送給每個人（1080P 3 人：跳轉後 12 秒平均 64～79 Mbps，接近預算上限）。種子式組回到 100 ms 內反而比對照組快，因為對照組房主要同時補三份超前量。附錄 D §4 的「小塊輪流送、邊收邊轉」原型沒做。
- **SHA-256**：4 MiB 約 2.2～2.5 ms（M1、`crypto.subtle.digest`）。
- **沒做成的**：
  - 1080P 15 Mbps **5 人**（較早版本的原型）：有 2 位收看者的 DataChannel 不再排空、播放停住（`results/swarm-1080p15-n5-overload.json`）。**待驗假說**：同一台 M1 上 6 個分頁各自解碼 1080P，加上 loopback 總流量，與附錄 A §2 的 loopback 停滯相同。
  - 4K 40 Mbps MKV（GOP 5 秒、每段 25 MB）**2 人**：收看者一直沒開播（`results/swarm-4k40-n2-stalled.json`）。推測原因是原型的兩個簡化：急件直送給每個人，加上整段 25 MB 收完才轉送；房主預算 50 Mbps 時，每段給兩人要 8 秒，比片段長度（5 秒）還久。這正是附錄 D 要求「片段 ≤ 2 秒／4 MiB」與「小塊輪流送、邊收邊轉」的原因；1 人時正常。
  - 以上要在多台機器上用正式規則驗證（T-147）。

**hls.js 的實際問題**（寫進 T-142 的注意事項）：

1. 自訂 loader 的回呼必須是**非同步**，而且 `abort()` 要呼叫 `onAbort`；否則 hls.js 在第一次 `BUFFER_RESET` 後永遠停在 `FRAG_LOADING`（原型踩到）。
2. 原型用影音同段的 fMP4，hls.js 建一個 `audiovideo` SourceBuffer（light build 沒有獨立音軌播放清單）。這**不符合**附錄 F §3 的分軌契約，正式版要改用完整版的獨立音軌（§2 門檻第 2 點）。
3. hls.js 以第一段的 `tfdt` 對齊播放清單時間（`initPTS`，原型的片從 0 開始所以一致）。附錄 B §3 的輸出時間軸要等於播放清單時間：起點不是 0、有 edit list、有起始空白的片，T-141 要用附錄 B §3 的素材驗證。
4. 長 GOP 切成的續接段不是獨立可解的。跳轉落在續接段時 hls.js 的行為未驗證；我們的追趕本來只跳到入口附近（附錄 C §3），T-142 要驗收「長 GOP 片跳轉」。
5. 播放清單要事先知道所有片段：MP4 從 `stss` 直接得到；MKV 靠 Cues。沒有 Cues 的 MKV 要掃描，大檔可能很慢，T-141 量測，太慢就這種片走第三層。
