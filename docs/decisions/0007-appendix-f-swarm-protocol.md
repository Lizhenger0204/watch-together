## §2 請求的生命週期

**識別碼**：`config`（同 B §1）；`epoch`＝**收看端**的定位世代，每次重新定位（加入、自己跳轉、依房主 `position`）加 1；`reqId`＝收看端配發、同一連線內遞增不重複的請求編號。

**開始**：`hello` → `probe` → `probeResult` → `config` → `segtable`（分頁）→ 收看端建好 MediaSource 後回 `ready { config }`，之後由收看端送 `req`。房主送 `position { config, entry, rateHint }` 表示「請你重新定位到 `entry`」（`stuck`、`quota` 或房主重新選入口時）：收看端開新 epoch、取消全部請求，照 B §4 第 4 步清緩衝與重設 append window，再從 `entry` 那一段開始要。

**init segment**：每個 config 一份，跟片段一樣用 `req` 要（`index = INIT`）。收看端留在記憶體，每次 `abort()` 之後自己重新附加，不必再要。

**接收空間預留**：送出 `req` 前，收看端預留這次要的位元組（`seg` 公布的大小）。**所有來源合計**「已預留＋已收到未附加」≤ 16 MiB；每個來源最多 2 個請求在途。急件需要空間時，先取消預讀的請求釋放預留。房主端另檢查：同一收看者向房主在途的請求 ≤ 16 MiB，超過算協定錯誤。

**取消與遲到的資料**：`cancel { reqId }`，來源丟掉佇列中的部分。取消後 5 秒內收到該 `reqId` 的資料：直接丟棄、不計入任何統計、不算違規。從沒發出過的 `reqId`，或取消超過 5 秒後才到：違規（附錄 D §5）。

**逾時與改派**：有效請求 3 秒沒有任何資料，或來源回 `nack { reqId }`（他已沒有這段、或不再轉送），收看端取消並送 `where` 請房主改派；急件直接向房主要。

**ICE restart**：識別碼不變，逾時的請求照上面重發；中斷超過 5 秒才恢復時，收看端開新 epoch。換 `pt-data`（C §4 的排空逾時）時，舊頻道上的請求全部視為取消、在新頻道重發。

**片尾**：`segtable` 的最後一頁帶 `last: true`，最後一段的 `flags` 標示結尾。最後一段附加完成、待附加佇列為空、所有 SourceBuffer 都不在 `updating` 才呼叫 `endOfStream()`；C §1 其餘規則不變。`state.ended` 不變。

**quota**：照 C §4 清除並重試一次；仍失敗就把自己的 `LEAD_BYTES` 減半（下限 16 MiB）、開新 epoch 自行重新定位，並回報 `quota`。同一 config 第 3 次就送 `fail`，房主讓他降層。

**ManagedMediaSource**：`endstreaming` 時取消所有預讀請求、停止發新請求；`startstreaming` 時從 E 之後的緩衝末端繼續要。

**C §3 的 `r`**：收看端此刻可取得的連續資料速率 = `min(過去 3 秒實際收到的速率, 指派給他的來源配額合計)`；剛加入沒有量測時用房主在 `position`／`config` 給的 `rateHint`。

**片段必須可重現**：同一 `(config, index)` 的位元組必須與公布的雜湊相同。第一層的封裝器必須是確定的（不寫時間、亂數），T-141 以「同一段封裝兩次位元組相同」驗收。第二層的轉碼不保證可重現：房主保留已公布的轉碼片段 `[E − 30 秒, E + LEAD_S]`；需要重新產生已公布的段（快取已清、編碼器重設、往回跳出保留範圍）時，改開新的 config（新的轉碼世代），收看者在下一個入口段切換。

## §3 分框與小塊

- **小塊**：片段的位元組每 256 KiB 一塊（最後一塊較短），`seg.pieces` 是每塊的 SHA-256。片段 ≤ 4 MiB，所以最多 16 塊。
- **每則訊息** = 20 bytes 標頭 + 資料，整則 ≤ `chunk`（B §2）。一塊分成多則連續送出，同一條頻道上一次只送一塊。標頭（big-endian）：

  | 位移 | 長度 | 欄位 | 說明 |
  | --- | --- | --- | --- |
  | 0 | 1 | `kind` | 1 = init，2 = 片段 |
  | 1 | 1 | `flags` | bit0 = 這一塊的最後一則 |
  | 2 | 2 | `piece` | 塊序號 |
  | 4 | 4 | `config` | |
  | 8 | 4 | `index` | 片段序號（init 為 `0xFFFFFFFF`） |
  | 12 | 4 | `reqId` | |
  | 16 | 4 | `offset` | 塊內位移 |

- **驗證與轉送**：收齊一塊就比對雜湊；通過才標記為已有，並可**立刻**轉送給向他要這一塊的人（邊收邊轉）。整段的每一塊都通過，才把這段交給 MSE；同一 epoch 內依片段順序附加，先到的後段等前段。
- **請求範圍**：`req` 帶 `pieces: [a, b)`，所以同一段可以由不同來源各送一部分（跳轉時輪流送，附錄 D §4）。
- **片段表**：每段 `[start, end, flags]`，`flags` bit0 = 入口段（可獨立解碼），bit1 = 最後一段。

## §4 訊息

| 方向 | type | 內容 |
| --- | --- | --- |
| 房主 → 收看者（`pt-ctl`） | `segtable` | `{ config, page, segs: [[start, end, flags], …], last }` |
| | `seg` | `{ config, index, size, pieces: [sha256, …], sources: [{ from: 'host' \| memberId, pieces: [a, b) }, …] }`（公布＋指派；改派時再送） |
| | `position` | `{ config, entry, rateHint }` |
| | `drop` | `{ peer }`：不要再向他拿 |
| | `audit` | `{ config, index, piece }`：請他把手上的這一塊送回房主（附錄 D §5） |
| 收看者 → 房主（`pt-ctl`） | `ready` | `{ config }` |
| | `have` | `{ config, ranges: [[a, b], …] }`，最多 16 段、每 500 ms（可替換）；回報的片段至少保留 5 秒 |
| | `req`／`cancel` | 同下（向房主要） |
| | `where` | `{ config, index }` |
| | `bad` | `{ peer, config, index, piece, reqId }` |
| | `relay` | `{ on, upMbps, reason? }` |
| 收看者之間（`sw-ctl`） | `req` | `{ reqId, config, epoch, index, pieces: [a, b) }` |

| 資料（`pt-data`、`sw-data`） | — | 二進位，§3 |

- 收看者之間只接受「房主指派給我、我向他要過」的請求與資料；其他算違規。速率上限、單則大小、可替換訊息的規則同 B §4。

## §5 收看者之間的信令（規則改變）

現行規則（`AGENTS.md`、`protocol.md`）：收看者的 `signal` 只能送給房主。種子式散布改為下列規則。

**配對紀錄**：RoomDO 的房間狀態裡記 `swarm = { on, liveSession, pairs: [{ pairId, a, b, aConn, bConn }] }`：`liveSession` 是房主目前的直播工作階段（protocol.md「房主重新連線」每次驗證成功都是新的），`aConn`／`bConn` 是雙方登記當下、已完成 `auth` 的 WebSocket，`pairId` 在房內遞增不重複。全部在既有的 `changes` 佇列內讀寫，與席位同一筆交易提交。

1. `swarm:mode { on }`、`swarm:pair { a, b }`、`swarm:unpair { a, b }` 只有房主能送。`swarm:pair` 在佇列內檢查：模式已開、兩人此刻都是本房在線且已 `auth` 的收看者、房主的直播工作階段沒變，然後**先提交**，提交後才送 `swarm:paired { peer, pairId }` 給雙方。收看端收到 `swarm:paired` 才開始協商。
2. 收看者 X → Y 的 `signal { to, pairId, data }`：在佇列內、**實際送出前**確認：配對存在且 `pairId` 相符、X 的連線就是 `aConn`／`bConn` 之一、Y 此刻的連線就是登記的那條、模式仍開、直播工作階段沒變。轉送時帶 `pairId`；收看端只接受與目前配對相符的 `pairId`，舊配對的 SDP／candidate 直接丟掉。
3. **撤銷**（與觸發的變更同一筆交易）：踢出、離開、心跳逾時（`4410`）、同一成員新連線取代舊連線（`4000`）、房主重新連線（新的直播工作階段，撤銷全部）、停播、關閉模式、切到轉發、房主 `swarm:unpair`。撤銷後送 `swarm:unpaired { peer, pairId }` 給還在線的一方，他關閉與對方的連線。
4. **Durable Object 喚醒**：配對存在 storage，但喚醒後若無法確認登記的連線仍是同一條（休眠連線的附件對不上），該配對一律撤銷。
5. **統一的拒絕**：收看者送給收看者的 `signal`，凡是授權不通過（對方不存在、不在線、沒配對、`pairId` 過期、模式已關）一律回 `error { code: 'FORBIDDEN' }`、同一句訊息，不透露原因。只有與對象無關的格式錯誤回 `BAD_REQUEST`。現行「房主 ↔ 收看者」的回應不變。

**使用者決定（2026-11-27）**：同房的人可以互相看到 IP；沒有邀請碼、沒進房的人絕不能拿到任何人的 IP。這項保證涵蓋**本產品的信令、REST 端點、錯誤訊息與 log**；IP 只會出現在實際建立直連的成員之間（房主與每位收看者、配對的收看者）。撤銷只能阻止之後的交換，已取得的位址無法收回。
