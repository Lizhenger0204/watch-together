# ADR 0007 附錄 D：種子式散布規則草稿（T-140）

> **草稿（T-140）**：ADR 0007 採用前沒有效力。只在 **P2P 模式**、房主開啟「收看者互相轉送」時生效；關閉時照附錄 B、C。單位同附錄 C。套件評估與原型結果見[附錄 E](0007-appendix-e-swarm-libs.md)。

## §1 前提

- 房主是**唯一來源**（只有他有檔案）與**時鐘**；收看者只轉送自己已收到、已驗證的片段。房主離線時全房停止，與現在相同。
- 每房最多 7 位收看者（`ROOM_MAX_MEMBERS = 8`，含房主）。
- 「散布」只看同一個 config：`hev1` 與 `hvc1` config、第二層每種畫質，各自是一群；收看者只轉送自己那一群的片段。第三層不參與。

## §2 資料模型：固定片段表、收看端主動要

種子式散布要讓不同的人拿到**位元組完全相同**的片段，所以第一層的資料改為：

- **片段表**：房主開片時依關鍵影格切出固定的片段（影像與同時段的音訊放在同一個片段，兩組 `moof`／`mdat`）。每段以入口（附錄 B §3 的規則）開頭；GOP 超過 2 秒或封裝後超過 4 MiB 時，在 sample 邊界依固定規則切成續接段。同一 config 的片段表與片段內容是確定的，ID = `(config, index)`。片段表很長時（2 小時約 3,600 段）分頁送，不受 `pt-ctl` 單則 16 KiB 的限制。
- **收看端主動要**：收看端依自己的播放位置向指派的來源要片段（`req`），不再由房主依 epoch 推一條專屬的串流。房主自己也只是「每段都有」的來源。加入、跳轉只是改變「現在要哪幾段」，不需要每人一個 epoch 的資料流；附錄 C §3 的入口公式仍用來決定「從哪一段開始要」。
- **關閉種子式散布時也用同一模型**（來源只有房主）。這樣 T-142 不必先做一套推送式、之後再改。附錄 B §2 的塊標頭改為 `kind | config | index | piece | count`（`epoch`、`seq` 不再需要）；附錄 C §4 的雙邊背壓改為「每個來源最多 2 段在途、收看端待處理 ≤ 16 MiB」。

## §3 拓撲比較

| | **A. 房主協調**（建議） | B. 各自交換持有清單（類 BitTorrent） |
| --- | --- | --- |
| 誰決定向誰拿 | 房主依各人的持有清單、上傳預算指派來源 | 各收看者看鄰居的 `have`，自己挑（最接近播放位置優先、其次最稀有） |
| 控制訊息 | 收看者 → 房主：`have`（每 500 ms，以區段表示）；房主 → 收看者：`seg` 指派 | 鄰居之間廣播 `have`、互送 `req`；房主只公布雜湊 |
| 房主預算與選層 | 房主知道每份從哪裡來，可以直接算（§8） | 只能事後觀察，難保證某人一定放得下 |
| 搭便車、上傳過量 | 房主只指派願意上傳、還有餘量的人 | 要另做 choke／unchoke 才公平 |
| 新人加入 | 房主把現有持有者分給他（最多 3 個平行來源） | 新人向鄰居要；鄰居剛好沒有就慢 |
| 離開或卡住 | 房主 1 秒內重新指派 | 各自逾時後換人 |
| 每人最多幾個 peer | 3 位收看者＋房主 | 同左（數量相同，只是由誰挑來源不同） |
| 信令 | 配對本來就由房主決定（§6），沿用信令伺服器 | 也需要房主指派鄰居（§6 的安全規則），沒有省下 |
| 實作與測試 | 邏輯集中在房主，是純函式，好做單元測試 | 分散、行為是湧現的，難重現 |
| 適用規模 | 每房 ≤ 7 人綽綽有餘 | 大型群體 |

**建議 A**。房主本來就是來源與時鐘；房間很小，房主手上的資訊足夠做最佳指派；而 §6 規定配對由房主決定，B 的去中心化在這裡得不到好處。

**每人最多 3 個 peer**：房主挑鄰居，讓任兩位收看者之間最多隔一人（7 人時每人 3 個鄰居做得到）。收看端的 `RTCPeerConnection` 總數 ≤ 4（含房主）。

## §4 排程（房主協調）

**房主每產生一段（或有人要了還沒公布的段）**：

1. 算 SHA-256（§5），把 `seg { config, index, size, pieces, from }` 送給這一群的每個人。`from` 是房主替他選的來源。
2. **直送份數 k**：房主**先用自己的頻寬**，k = 房主預算放得下的份數（§8），至少 1。直送的對象依片段輪流挑選「願意上傳、還有餘量」的人，讓上傳量平均分攤。
3. 其他人：從「已有或即將拿到這段」的鄰居中挑剩餘上傳量最多的；層數最多 3 跳（房主 → A → B → C）。
4. 每位上傳者被指派的總量 ≤ 他的上傳預算（§7）。

**急件與預讀**（收看端以「應在時間 E」判斷）：

| 類別 | 範圍 | 來源 | 逾時 |
| --- | --- | --- | --- |
| 急件 | 片段開始時間 < E + 3 秒，或播放器正在等 | 房主有餘額時**直送**（跳轉、開播的第一批）；沒有餘額時依指派 | 指派的來源 1.5 秒沒開始到，改向房主要 |
| 預讀 | E + 3 秒 ～ E + `LEAD_S` | 依指派（種子） | 片段開始時間進入急件範圍時，照急件處理 |

- 每個送出佇列都依「片段開始時間」排序：急件插到預讀前面（不中斷正在送的那一小塊）。房主的上傳順序：控制訊息 > 急件補送 > 新片段直送 > 加入與跳轉的追趕 > 其他。
- **跳轉**：所有人同時需要新位置的片段。房主把新位置前 3 秒以 256 KiB 小塊**輪流**送給不同的人，大家邊收邊轉（§5 的小塊雜湊讓收到一塊就能轉一塊），整房的上傳一起分擔。估計：4K 40 Mbps、7 人，若全由房主直送 3 秒資料要約 11 秒；分攤後約 3 秒（最慢的一跳受限於 `(n − 1) × 3 秒資料 ÷ 收看者總上傳`）。
- **加入**：新人要 `[入口, E + LEAD_S]`。房主把這段範圍分給最多 3 位持有者（大家都留有已播 10 秒、超前 20 秒的資料），入口那一段優先由房主直送。
- **離開**：房主撤銷他的配對（§6），把他還沒交付的指派改給其他持有者或房主自己。收看端發現連線關閉時送 `where` 請房主改派。
- **卡住**：某位上傳者 3 秒沒有進度（指派給他的對象回報 `receivedBytes` 不動），或他自己回報 `buffering`／`relay { on: false }`：60 秒內不再指派他當來源，已指派的改派。
- **片尾**：最後一段照常散布；`kind = 4` 的送完標記只由房主送。

## §5 完整性

- 房主對每段的每個 **256 KiB 小塊**算 SHA-256，隨 `seg` 在 `pt-ctl` 送出（`pieces` 是雜湊陣列；4 MiB 一段 16 個，約 1 KB）。init segment 與片段表也帶雜湊。`pt-ctl` 只有房主那條（DTLS、經伺服器驗證身分建立），收看者之間的頻道不傳雜湊。
- 收看端收到每一小塊就比對；**通過的小塊才附加、才轉送**。超過宣告的 `size`、小塊數不符就立刻斷開這次傳送。
- 驗證不過：丟掉整段，改向房主要（`req`），送 `bad { peer, config, index }` 給房主，自己 10 分鐘內不再向那位要。
- 房主收到 `bad`：先停用「這一對」的指派；**兩位以上不同的收看者**檢舉同一位，或房主自己驗到（房主有原檔可比對），才全面停用他當來源，並向伺服器撤銷他的所有配對。避免一位收看者誣告別人就能把對方踢出散布。
- SHA-256 很便宜：M1 上 4 MiB 約 2 ms（附錄 E §3）。**不需要整檔雜湊**：每段在產生時才算，50 GB 的片也能立刻開播。

## §6 安全與信令（**規則改變**）

**現行規則**（`AGENTS.md`、`protocol.md`）：收看者的 `signal` 只能送給房主，伺服器擋下送給其他收看者的。種子式散布需要收看者之間建立連線，**改為**：

伺服器只在**以下全部成立**時轉送收看者 X → 收看者 Y 的 `signal`：

1. 房主已對這個房間開啟種子式散布（`swarm:mode { on: true }`，只有房主能送，存在 RoomDO storage）。
2. 房主已登記 `(X, Y)` 這一對（`swarm:pair { a, b }`，只有房主能送；伺服器檢查兩人此刻都是本房、已完成 `auth`、未被踢出的成員）。
3. X 的連線已完成 `auth`；Y 此刻在線且已完成 `auth`。

其他情況一律擋下，回應與現在相同的錯誤（不透露 Y 是否存在、是否在線）。

**使用者決定（2026-11-27）**：同一個房間的人**可以**互相看到 IP；**沒有邀請碼、沒有進房的人絕不能拿到任何人的 IP**。檢查點：

| # | 規則 | 驗證 |
| --- | --- | --- |
| 1 | 只有已用邀請碼進房、持有效 `memberToken` 並完成 `auth` 的連線，才收得到任何 SDP 或 ICE candidate（房主與收看者之間、收看者之間都一樣） | 伺服器單元測試：未 `auth` 的連線收不到 `signal`；E2E 見 #5 |
| 2 | 公開或未驗證的端點（REST 房間資訊、加入前的查詢、錯誤訊息、log）不帶 IP 或 candidate；伺服器不記錄 `signal.data` | 伺服器測試：所有 REST 回應與錯誤訊息不含 `candidate`／`sdp` 欄位；log 檢查 |
| 3 | 被踢出或離開：伺服器立刻刪除他的所有配對，不再轉送任何 `signal` 給他或來自他；對方收到 `swarm:unpaired { peer }` 後關閉與他的連線。房主重新產生邀請碼後，舊碼不能進房 | 伺服器測試；E2E 見 #5 |
| 4 | **第一道防線是邀請碼**：沿用現行的防暴力猜測（限流、錯誤一律同一種訊息、可重新產生，見 room-and-invite.md） | 既有測試 |
| 5 | **E2E**：(a) 只連上 WebSocket、沒有 `auth` 的連線，(b) 被踢出的成員，在整個測試期間都收不到任何含 candidate 的訊息；(c) 沒有配對時，收看者送給收看者的 `signal` 被擋下；(d) 配對撤銷後同上 | T-146 |

- 收看者之間只用 STUN（沿用現行設定，不只 Google），**不給 TURN**：TURN 流量要付費，直連不上就那一對不配對，改向其他鄰居或房主拿。
- Chrome 的 host candidate 是 mDNS（不露內網 IP），公網 IP 會出現在 srflx candidate。
- 協議變動（T-146 先改 `protocol.md` 與 `packages/shared`）：新增 `swarm:mode`、`swarm:pair`、`swarm:unpair`（房主 → 伺服器）與 `swarm:paired`、`swarm:unpaired`（伺服器 → 收看者）；`signal` 的「收看者只能送給 host」改為上面的條件。`AGENTS.md` 的對應句子由協調者在採用時更新。

**提示文字**：

- 房主開啟時：「開啟『收看者互相轉送』後，收看者會把收到的影片片段轉送給同房間的其他人，減輕你的上傳負擔。同一房間的人會互相看到對方的網路位址（IP）；沒有邀請碼的人看不到。每個片段都會用你這邊發出的校驗碼檢查，被改過的資料會被丟掉。」
- 收看者進房（已開啟時）：「這個房間開啟了『互相轉送』：你會和同房間的其他人直接連線（彼此看得到 IP），也可能把已收到的片段轉送給他們。用手機網路或上傳較慢時，可以在設定關閉『幫忙轉送』，只下載。」

## §7 收看者的上傳

- **開關「幫忙轉送」**，收看者隨時可關。**預設不上傳**（只下載）：手機與平板（UA-CH `mobile`、iOS／iPadOS、Android）、`navigator.connection` 顯示 `cellular` 或 `saveData`、分頁進入背景超過 10 秒（iOS 背景會暫停）、宣告的上傳頻寬 < 5 Mbps。桌面瀏覽器預設：待使用者決定（ADR 待決事項）。
- **上傳預算** = 收看者選的上傳頻寬 × 0.5（房主是 × 0.7，收看者還要顧自己的下載）。選項：不轉送／10／30／50／100 Mbps；之後可加自動量測。以 token bucket 配速（附錄 C §4 條件 1），所有鄰居共用一個。
- **不擠掉自己的下載**：自己的超前量 < 5 秒或接收速率連續 3 秒低於 1.1 × 片源位元率時，上傳預算減半；超前量 < 2 秒時暫停轉送並回報 `relay { on: false, reason: 'self' }`，恢復到 10 秒以上再開。
- **轉送快取**：MSE 的緩衝讀不回來，要另外在記憶體留一份已驗證的片段，範圍 `[E − 10 秒, E + LEAD_S]`、上限 96 MiB。記憶體不足的裝置（`navigator.deviceMemory ≤ 4`）不轉送。

## §8 與三層的關係、房間預算

- 第二層：房主每種畫質只轉碼一份，這份照同樣規則在需要的人之間散布。第三層不變（房主對每人一份 RTP）。
- 開啟種子式散布時，附錄 C §5 的分配改為：
  1. `B = 房主上傳 × 0.7`。依加入順序把每位收看者放進候選層（同附錄 C §5）。
  2. 每一群（config）c：人數 `n_c`、每份 `p_c = 1.1 × b_c`。房主直送 `k_c = min(n_c, ⌊剩餘 0.8B ÷ p_c⌋)`；`k_c = 0` 表示房主連一份都送不起，這群的人改下一層。
  3. 這群願意轉送的人上傳預算合計 `U_c`。需要 `U_c ≥ 1.1 × (n_c − k_c) × p_c`（多 10% 的餘量）。不夠時：房主預算還有就把 `k_c` 加 1，否則把這群**最晚加入、不轉送**的人改下一層，重算。
  4. 追趕餘額 `A = B − Σ k_c × p_c − 第三層預留`，留給急件、補送、加入與跳轉。
- 例：房主上傳 110 Mbps（`B = 77`、`0.8B = 61.6`），收看者都願意轉送、上傳都夠：

| 片源 | 收看人數 | 全部由房主直送 | 種子式：房主送 | 房主省下 | 收看者合計上傳 | 每位平均上傳（需宣告約 2 倍） |
| --- | --- | --- | --- | --- | --- | --- |
| 4K 40 Mbps（每份 44） | 3 | 132（放不下，現行只有 1 人能看原片） | 44（k = 1） | 88（67%） | 88 | 29 |
| | 5 | 220 | 44 | 176（80%） | 176 | 35 |
| | 7（滿房，共 8 人） | 308 | 44 | 264（86%） | 264 | 38 |
| 1080P 15 Mbps（每份 16.5） | 3 | 49.5（放得下） | 49.5（k = 3） | 0 | 0 | 0 |
| | 5 | 82.5（現行 3 人原片） | 49.5 | 33（40%） | 33 | 7 |
| | 7 | 115.5 | 49.5 | 66（57%） | 66 | 9 |

- 1080P 若改成房主只送 1 份（k = 1）：房主 16.5，省 67%／80%／86%，但每位收看者要上傳 11／13／14 Mbps。建議照上面「房主先用自己的頻寬」，收看者只補不足的部分。
- **收看者要付出的**：4K 40 Mbps 每人平均上傳約 29～38 Mbps（宣告的上傳要約 60～76 Mbps）；上傳不夠的人只能部分轉送，總量不夠時有人改看轉碼。另有記憶體（最多 96 MiB）與彼此看得到 IP。
- 房主的 RTP（第三層）照現行規則；第三層收看者不轉送。

## §9 訊息（草稿，T-141 定案）

| 頻道與方向 | type | 內容 |
| --- | --- | --- |
| `pt-ctl` 房主 → 收看者 | `segtable` | `{ config, page, segs: [[start, end], …], last, sha256 }`（分頁） |
| | `seg` | `{ config, index, size, pieces: [sha256, …], from: 'host' \| memberId }`（公布＋指派；改派時再送一次） |
| | `drop` | `{ peer }`：不要再向他拿 |
| `pt-ctl` 收看者 → 房主 | `have` | `{ config, ranges: [[a, b], …] }`，最多 16 段、每 500 ms 一次（可替換） |
| | `req`／`where` | `{ config, index }`：向房主要／請房主改派 |
| | `bad` | `{ peer, config, index }` |
| | `relay` | `{ on, upMbps, reason? }`：轉送意願與上傳預算 |
| `sw-ctl` 收看者之間 | `req`／`cancel` | `{ config, index }` |
| `sw-data` 收看者之間 | — | 二進位，塊標頭同 §2 |

- 收看端只接受「自己向那位要過」的片段；沒要過就送來、超過 `size`、小塊雜湊不符都算違規：關閉這一對並回報 `bad`。
- 速率上限、單則大小、可替換訊息的規則同附錄 B §4。
