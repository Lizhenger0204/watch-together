# 規範：房間與邀請碼

## 角色

| 角色 | 取得方式 | 權限 |
| --- | --- | --- |
| host（房主） | 建房者，持有 `hostToken` | 選片開播、切換模式、切換畫質、重新產生邀請碼、鎖房、踢人、聊天室發言 |
| member（收看者） | 用邀請碼加入，持有 `memberToken` | 觀看、聊天室發言 |

- 每房只有一位房主，房主斷線不轉移。**房主斷線或重新驗證（含另一分頁以 4000 取代）時，伺服器立即把直播狀態改為未開播**並通知收看者（顯示房主離線）；房主重新連線並準備好片源後要再送 `stream:status { live: true, title }`。若房主連續離線滿 **100 秒**（`ROOM_HOST_OFFLINE_TTL_MS=100000`）仍未重新驗證，伺服器自動移除房主席位、撤銷其 `hostToken` 與轉發發布（含綁定訂閱）並廣播 `room:members`。若房內仍有收看者，房間先保留（收看者可繼續聊天、畫面提示房主已離開，既有成員仍可沿用原身份重連，但不再接受新成員以邀請碼加入，一律回 `404 ROOM_NOT_FOUND`），直到房內已無任何成員（立即關房）或無人在線滿空房期限（`ROOM_IDLE_TTL_MS=100000`）才釋放房間與邀請碼。
- 房間欄位 `mode`：`p2p`（預設）或 `relay`。

## 邀請碼

- 長度 8，字元集 `23456789ABCDEFGHJKMNPQRSTUVWXYZ`（去掉易混淆的 0/O/1/I/L）。
- 顯示格式 `ABCD-EFGH`。輸入時不分大小寫，忽略 `-` 與空白。
- 用 `crypto.getRandomValues` 產生（Workers 環境），不可用 `Math.random`。
- 對照表存在 `InviteDirectoryDO`（單一實例，強一致），寫入時檢查是否與現存邀請碼衝突。
- 房主可「重新產生」：舊碼立即失效，已在房內的人不受影響。
- 前端提供「複製邀請碼」與「複製邀請連結」（`/join/ABCDEFGH`）。

## Token

- `hostToken`／`memberToken`：32 bytes 隨機，base64url。伺服器只存 SHA-256 雜湊，比對時用常數時間比較、逐一比完所有成員。
- 前端存在 `localStorage`（key：`room:<roomId>:token`），重新整理或重連時恢復身份。
- 傳送方式：
  - REST、WHIP、WHEP：`Authorization: Bearer <token>`。
  - WebSocket：瀏覽器無法自訂 header，**連線後第一則訊息送 `auth { token, protocolVersion }`**，5 秒內沒有通過驗證就斷線。
  - **不可放在 URL query**。

瀏覽器已記住邀請碼與房號的對照時，點該連結是既有成員的回房捷徑。即使房主已換碼，仍須以房間的有效憑證通過 `GET /ice`；失效的舊碼不能讓新人取得席位。前端在同源加入鎖內重新讀取共用儲存，採用其他分頁最新寫入的身份。暫時性錯誤保留身份，讓使用者重試。明確收到 401 或 404 時只處理失效的舊身份，本次請求不另配席位。

遇到新碼時，前端在配置席位前排除本機已持有身份的房間，對同房的現行邀請碼用原憑證沿用席位。沿用不改變角色或暱稱，房主換碼、鎖房或滿房時仍可回房。沿用失敗的 404 也可能只是錯房或錯碼。前端另用原憑證呼叫該房的 `GET /ice`，只有 401 或 404 且憑證值仍相同才清除。自然淘汰或被踢者可在下一次明確提交現行碼時重新加入。

配置席位與保存身份之間可能中斷（例如分頁關閉）。前端在同源加入鎖內若該邀請碼沒有尚未確認結果的待完成鍵，就為這次新加入產生一把加入冪等鍵，先寫進共用儲存（key：`join:<邀請碼>:key`，值附建立時間），再送出加入請求（protocol.md「加入冪等」）。只有前一次請求結果未明（網路中斷、回應遺失、`500`、分頁關閉、既有待完成鍵重試遭限流，或憑證無法寫入持久儲存而鍵已持久化）時才保留這把鍵，讓 5 分鐘內的重試與接手加入鎖的其他分頁沿用同一把鍵、只配同一席。一旦身份寫入持久儲存、成功沿用既有身份，或伺服器明確未配位（`404`／`409`，或本次新產生之鍵在進房前被拒），前端分別核對持久儲存與本分頁記憶體，只條件清除與自己相符的那份；之後再按加入是新操作，改產生新的鍵。超過 5 分鐘的鍵自動清除，不再使用也不在儲存空間累積。這把鍵和 token 一樣是機密。

有超過 16 個本機房間身份時，先以 `GET /ice` 清理確定失效的身份，降到上限內即可送出完整排除名單。若仍超過上限，逐房嘗試沿用，待舊身份失效後才能配置新席，避免截去房號而重複配位。遇到加入限流時由使用者稍後重試，從尚未比對的房號開始。

## 生命週期（RoomDO，用 Durable Object alarm 計時）

| 事件 | 行為 |
| --- | --- |
| 建房 | 狀態 `open`，並啟動房主未連線計時 |
| 房主鎖房 | 狀態 `locked`，拒絕新加入，現有成員不受影響 |
| 房主離線滿 100 秒 | 移除房主席位、作廢 `hostToken` 與轉發發布（含綁定訂閱）並通知在線成員；若房內已無成員則立即關房 |
| 主動離開房間 | 呼叫 `POST /api/rooms/:roomId/leave` 移除呼叫者席位與憑證；若為房主且仍有收看者則停播並保留房間；若房內已無成員則立即關房 |
| 最後一人離開 | 啟動 100 秒空房計時（`ROOM_IDLE_TTL_MS=100000`），期間有人回來則取消 |
| 房內成員數歸零、空房計時到期或建房滿 24 小時 | 關閉房間、斷開所有連線、刪除邀請碼對照、關閉轉發模式的 Realtime tracks |

- 建房後若房主未在 `ROOM_HOST_OFFLINE_TTL_MS`（預設 `100000`，100 秒）內完成 WebSocket 驗證，同樣移除房主並釋放空房。
- 舊版房間喚醒時若缺少 `hostDisconnectedAt`，房主不在線時以 `host.lastSeenAt` 推算；若由一次性空房巡檢發現缺少 `idleSince` 且未逾 24 小時，改自首次確認無人在線當下起算 100 秒。
- 上個版本遺留未釋放的空房與孤兒邀請碼由 `InviteDirectoryDO` 一次性巡檢（依 `sweep:version`）分批喚醒各 `RoomDO` 自動清理：已到期（含 `idleSince` 逾 100 秒或建房逾 24 小時）的空房與已逾期的孤兒邀請碼立即釋放；缺少 `idleSince` 且無人在線的未逾 24 小時舊房自首次確認無人在線當下起算 100 秒空房期限（不以舊版不完整的 `lastSeenAt` 回推）；建房中的預留邀請碼與仍有成員在線的房間不受影響。

關房分兩步：

1. 先在 storage 用同一筆交易記下「關房中」並刪掉房間狀態，**提交成功後**才通知成員（`room:closed`）並以 `4001` 斷線。提交失敗時房間維持原狀，下次 alarm 再關。之後的加入、連線、WHIP／WHEP 一律視為房間不存在。
2. 再清理外部資源：邀請碼對照、轉發 tracks。**邀請碼與每個轉發資源各自嘗試、完成一項就保存一項**，其中一項失敗不會擋住其他項。

轉發待辦與其重試狀態、下一次 alarm 在同一筆交易提交。SFU 關閉 tracks 時回 `410 session_error` 表示 session 已結束，該項清理即完成。

有沒做完的就用 alarm 重試：間隔 30 秒起，每次加倍，最多 1 小時。**最多嘗試 12 次，包含關房當下的第一次**（即第一次之後再重試 11 次）。全部完成才刪除這個房間的 storage。

12 次都沒做完就放棄：記錄 `room.cleanup_gave_up`（只記次數與剩餘數量，不記邀請碼或 session），不再排 alarm。storage 裡**保留沒做完的紀錄**，包括還沒釋放的邀請碼、還沒查回結果的換碼操作、還沒關閉的轉發資源，以及嘗試次數。房間狀態與成員資料在第 1 步就已刪除，不會保留。留著的邀請碼對照仍指向這個房間，但房間已不存在，用它加入一樣回 `404`。

到期關房（空房閒置 100 秒或滿 24 小時）會在取得執行權時用最新狀態重算期限。排隊期間如果有人回來，或計時已重設，就不關房，改排下一次 alarm。

重新產生邀請碼與關房在 RoomDO 內依序執行：**最後一次換到的碼有效，對照表不留孤兒**，且換碼交易會一併清空舊碼時期的加入冪等紀錄並遞增 `inviteCodeVersion`。依序執行時，第二次重產本來就會讓第一次的碼失效；同一個房主分頁在重產請求完成前停用重產按鈕，依序送出請求。換碼 REST 回應與房主的 `room:updated`／`room:snapshot` 都攜帶同一個單調遞增的 `inviteCodeVersion`，前端一律保留版本較高的邀請碼，畫面顯示該版本或更新的有效碼時才提示換碼成功。重新驗證後，房主以最新的 `room:snapshot` 顯示邀請碼。

換碼時，RoomDO 先在 storage 記下這次操作的識別碼（opId），再請邀請目錄換碼。邀請目錄在同一筆交易保留新碼、釋放舊碼並記錄結果。邀請目錄用 opId 記住每個房間最後一次換到的碼，同一個 opId 再呼叫會回傳同一個結果。所以邀請目錄已經換好、但 RPC 回應遺失時，下次重產或關房會用同一個 opId 查回那個碼，先套用或釋放，不會留下孤兒。

數值放在 `apps/signal/src/config.ts`，可由 `wrangler.toml` 的 `[vars]` 覆寫。

## 限制與防暴力猜測

- 每房最多 8 人（房主 + 7 位收看者，`ROOM_MAX_MEMBERS=8`），滿員回 `409 ROOM_FULL`。離線超過 10 分鐘的收看者在有人加入時會被移除以騰出名額（他們的 token 也隨之失效，要重新用邀請碼加入）。
- `POST /api/rooms/join`：每 IP（`CF-Connecting-IP`）每分鐘 10 次，超過回 `429`。使用 Workers Rate Limiting binding（`wrangler.toml` 的 `JOIN_RATE_LIMITER`）。沒有綁定或綁定出錯時，改用記憶體後備限流（同樣每 IP 每分鐘 10 次，只在單一 isolate 內計數，並記錄 `ratelimit.fallback`）。
- 邀請碼錯誤、房間已關閉、已鎖房、房主已離開或已移除：一律回 `404 ROOM_NOT_FOUND`，不洩漏房間是否存在。
- 暱稱：1–24 字，trim 後不可為空。前端顯示時必須跳脫（React 預設會做，不可用 `dangerouslySetInnerHTML`）。
- 聊天訊息：1–200 字純文字（不保留歷史紀錄，房主不需禁言或刪訊息），每位成員每 10 秒最多 5 則，超過回 `RATE_LIMITED`；被踢出者不可再發言。見 protocol.md「聊天訊息」。

## 主動離開房間

點擊「離開房間」時前端送出 `POST /api/rooms/:roomId/leave`：

- 收到 `204` 或伺服器明確回覆 `401 UNAUTHORIZED`／`404 ROOM_NOT_FOUND`（憑證已撤銷或房間已關閉）時，於同源加入鎖內條件清除本機與該憑證相符的身份及邀請碼對照（若另一分頁在退房途中寫入新憑證，保留新憑證）並返回首頁。
- 網路錯誤或 `5xx`（含回應遺失）時留在原頁、顯示錯誤訊息並保留憑證供重試。
- 房主主動離開且房內仍有收看者時，僅移除房主並保留房間（收看者可繼續聊天並看到房主已離開提示，且不再接受新成員加入），直到房內無人時釋放。

## 踢人

房主送 `room:kick` → 伺服器作廢該成員 token、斷開 WebSocket、通知房主關閉對應的 P2P 連線、廣播 `room:members`。被踢者用舊 token 重連會被拒絕。轉發模式下，伺服器也會關閉該成員的全部 WHEP tracks。

收看者自行離開頁面或斷線時，最後一條已驗證的連線關閉即清理該成員的 WHEP，席位與憑證依離線期限保留。新連線取代舊連線時，成員仍在線。成功加入觸發離線淘汰時，再清除被淘汰者名下的所有 WHEP。移除席位或切回 P2P 時，房間狀態與待清理資源一起提交。
